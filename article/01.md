Yes. I would make portability a **first-class architectural point**, not a footnote. Multipass is the implementation I chose for the local Mac lab, not a dependency of the Vault design. Your existing project already supports that argument because Ansible gets host data dynamically from Terraform and the Vault platform layer is independent of the VM layer.

# I Wanted Three Vault VMs on My Mac

## Building a portable Vault Enterprise lab with Terraform, Ansible, RHEL 9 and a replaceable virtualization layer

It started with a fairly innocent requirement.

I wanted three virtual machines on my Mac.

Each VM should run RHEL 9.

Vault Enterprise should run across all three.

The nodes should form a proper Integrated Storage cluster using Raft.

I wanted TLS, namespaces, secret engines, initialization, unseal, failover testing, drift detection and enough automation that I could destroy the entire environment and build it again.

And because this was supposed to become a useful lab rather than merely decorative:

```text
terraform apply
```

was not allowed to mean:

> Execute a giant pile of shell commands and hope everything ends up roughly where I wanted it.

The final architecture became:

```text
                    macOS / Apple Silicon
                             |
                             |
                   Terraform: Infrastructure
                             |
                             v
                      VM Substrate
                        Multipass
                             |
              +--------------+--------------+
              |              |              |
           vault-1         vault-2        vault-3
           RHEL 9          RHEL 9         RHEL 9
           ARM64           ARM64          ARM64
              |              |              |
              +--------------+--------------+
                             |
                          Ansible
                             |
                  TLS / Vault / systemd
                  license / configuration
                  bootstrap / unseal
                             |
                             v
                    Vault Enterprise
                    Integrated Storage
                           Raft
                             |
                             |
                    Terraform: Platform
                             |
               +-------------+-------------+
               |                           |
          engineering                  operations
          KV v2                        PKI
```

But the more interesting architecture is actually this:

```text
                 Infrastructure provider
                         |

                      Ansible
                         |
```

Multipass is only the first implementation of that infrastructure provider.

# Why RHEL VMs instead of containers?

I already run plenty of infrastructure locally using Docker and containers.

Vault runs very nicely in containers for many development and demo scenarios.

But that was not what I wanted to test.

I wanted something closer to the environments I regularly discuss with customers:

* RHEL
* systemd
* SELinux
* firewalld
* persistent filesystems
* TLS files with real ownership and permissions
* Vault running as a system service
* multiple hosts
* Raft communication between nodes

Containers abstract some of those things away.

That abstraction is normally a feature.

For this lab, it was exactly what I did not want.

The target therefore became three actual RHEL 9 ARM64 virtual machines running locally on Apple Silicon.

# Why I chose Multipass

The obvious first thought was VMware Fusion.

It is a perfectly capable desktop hypervisor and it can run ARM64 Linux guests on Apple Silicon.

But my real requirement was not:

> Can I create three virtual machines?

It was:

> Can I declaratively create, destroy and recreate three virtual machines as part of the lab?

That changes the decision.

I wanted the infrastructure layer to be:

* lightweight
* scriptable
* local
* reproducible
* easy to destroy
* easy to inspect
* friendly to cloud-init
* usable from Terraform

Multipass fitted that requirement very nicely.

It is open source, runs locally on macOS, and provides a simple command-line interface for creating and controlling virtual machines.

There is also a Terraform provider that exposes the Multipass lifecycle to Terraform.

One nuance is worth calling out.

The Multipass Terraform provider is community maintained, not an official HashiCorp or Canonical provider.

I was comfortable with that trade-off for a local lab because the interface is small and the infrastructure layer is intentionally isolated from the rest of the project.

That isolation turned out to be important later.

---

# Multipass is not the architecture

This is a distinction I want to make very explicit.

I did **not** design:

```text
Vault on Multipass
```

I designed:

```text
Vault on three RHEL machines
```

Multipass simply happens to create those machines in my current implementation.

The higher layers require a very small contract:

```text
hostname
IPv4 address
SSH connectivity
RHEL 9
```

If another platform can provide that contract, the remainder of the architecture does not need to care how the VM came into existence.

That means the infrastructure layer could be replaced.

For example:

```text
                      Terraform
                          |
         +----------------+----------------+
         |                |                |
     Multipass         VMware           Cloud
                        vSphere
         |                |                |
         +----------------+----------------+
                          |
                  Three RHEL VMs
                          |
                       Ansible
                          |
                   Vault Enterprise
                          |
                   Terraform Vault
```

VMware is a good example of why this distinction matters.

There is no equivalent Terraform provider specifically targeting VMware Fusion as a local desktop product.

But Terraform providers exist for VMware platforms such as vSphere, VMware Cloud Foundation and VMware Cloud.

So the same architecture could provision RHEL VMs into a VMware environment through a different Terraform provider and then hand those machines to exactly the same Ansible and Vault layers.

The same principle applies to other environments.

Conceptually:

```text
Multipass
Parallels
VMware vSphere
VMware Cloud Foundation
KVM / libvirt
Proxmox
AWS EC2
Azure Virtual Machines
Google Compute Engine
bare-metal RHEL
```

can all become infrastructure substrates.

The requirement is not that they look like Multipass.

The requirement is that the infrastructure adapter eventually produces something equivalent to:

```text

  hostname: vault-1
  ip:       192.168.x.x
  ssh:      reachable

vault-2
  hostname: vault-2
  ip:       192.168.x.x
  ssh:      reachable

vault-3
  hostname: vault-3
  ip:       192.168.x.x
  ssh:      reachable
```

From that point onward, Ansible can take over.

That turns the hypervisor into an implementation detail.

# The first interesting failure: Ubuntu assumptions inside RHEL

The RHEL VM booted.

SSH worked.

Networking worked.

The filesystem expanded correctly to 20 GB.

Yet:

```bash
cloud-init status
```

returned:

```text
status: error
```

That deserved investigation.

The actual failure was:

```text
Command: ['dnf', '-y', 'install', 'pollinate']
```

Multipass had injected vendor data containing:

```yaml
packages:
  - pollinate
```

`pollinate` makes sense in the Ubuntu ecosystem.

It makes considerably less sense inside a clean RHEL image with no enabled repositories.

The result was that cloud-init's final stage failed even though almost everything else had succeeded.

Initially I tried the apparently obvious fix:

```yaml
packages: []
```

It did not work.

Cloud-init's merge behavior preserved the vendor package list.

The eventual solution was much more surgical:

```yaml
#cloud-config

bootcmd:
  - [touch, /var/lib/cloud/instance/sem/config_package_update_upgrade_install]

package_update: false
package_upgrade: false
```

The semaphore tells cloud-init that its package installation module has already completed.

Everything else remains available:

* networking
* users
* SSH keys
* hostname configuration
* growpart
* filesystem resize

After rebuilding:

```text
status: done
extended_status: done
errors: []
```

and:

```bash
systemctl --failed
```

returned:

```text
0 loaded units listed.
```

That tiny problem became one of my favorite parts of the project.

Not because `pollinate` is particularly exciting.

Because it demonstrated why I prefer proving infrastructure manually before automating it.

If Terraform, Ansible, cloud-init, RHEL, Multipass and Vault had all been introduced simultaneously, that failure could have appeared to originate almost anywhere.

Instead, we knew exactly which layer owned it.

# Terraform owns machines

Once the VM lifecycle was proven, Terraform could take over.

The infrastructure layer has one responsibility:

> Make three healthy RHEL machines exist.

Nothing more.

```text
terraform/infra/
```

owns:

```text
vault-1
vault-2
vault-3
```

Each starts with:

```text
2 CPUs
4 GB RAM
20 GB disk
RHEL 9 ARM64
```

The lifecycle becomes:

```bash
make infra-plan
make infra
```

Terraform outputs the current addresses of the three machines.

That output is the contract between infrastructure provisioning and machine configuration.

What Terraform deliberately does **not** do at this stage is initialize Vault, store unseal keys, distribute licenses or become responsible for every operating-system mutation simply because it technically can.

Infrastructure provisioning and machine configuration are different responsibilities.

I wanted that distinction visible in the repository.

# The provider should be replaceable

Today:

```text
terraform/infra
       |
       v
todoroff/multipass
       |
       v
Multipass
```

Tomorrow it could be:

```text
terraform/infra
       |
       v
vmware/vsphere
       |
       v
vSphere
```

Or another infrastructure implementation.

The important design rule is:

> Do not let provider-specific behavior leak above the infrastructure boundary.

The ideal output contract is something like:

```hcl
nodes = {
  vault-1 = {
    hostname = "vault-1"
    ipv4     = "192.168.1.101"
    ssh_user = "ubuntu"

    hostname = "vault-3"
    ipv4     = "192.168.1.103"
    ssh_user = "ubuntu"
  }
}
```

Ansible should consume that contract.

It should not care whether Terraform created the VMs through Multipass, vSphere, a cloud provider or something else entirely.

That is what makes the architecture portable.

# TLS is real

I deliberately did not build the final lab with:

```hcl
tls_disable = true
```

The Ansible TLS role creates a local CA on the control machine and generates individual certificates for each Vault node.

The certificates contain the appropriate node and IP SANs.

They are then installed on the RHEL guests.

The certificate logic is also idempotent.

If a VM is rebuilt and receives a different IP address, the role can detect that the current certificate no longer contains the correct SAN and regenerate only what changed.

So even though this is a local lab, Vault communicates the way I actually want to demonstrate it:

```text
client
   |
   | TLS
   v
Vault API :8200

vault-1
   |
   | cluster communication
   v
vault-2 / vault-3 :8201
```

This is a lab.

There is no requirement for it to be unnecessarily fake.

# Secrets should not leak out while building a secrets platform

This sounds obvious.

It still deserves explicit design.

The project creates several highly sensitive artifacts:

```text
.secrets/
├── keys/
│   └── vault.hclic
├── tls/
│   ├── ca.key
│   └── node private keys
├── vault-init.json
└── platform-token
```

The initialization file contains the initial root token and Shamir unseal keys.

That file is created locally with restrictive permissions.

Ansible tasks handling tokens, unseal keys and license material use:

```yaml
no_log: true
```

The license is installed on each node with controlled ownership and permissions.

The root token is treated as break-glass material.

Day-to-day Terraform configuration uses a scoped platform token instead.

This became another architectural boundary:

> Terraform can manage Vault without owning Vault's bootstrap secrets.

That distinction matters.

The platform layer manages secret infrastructure:

* namespaces
* mounts
* policies
* authentication configuration

It does not need to become another database containing the secrets themselves.

# Bootstrapping the cluster

The sensitive Ansible bootstrap role handles the transition from three Vault processes to one Vault cluster.

The workflow is roughly:

```text
vault-1
   |
   +--> initialize
   |
   +--> unseal
   |
   +--> become initial Raft member
             |
             +------ vault-2 joins
             |
             +------ vault-3 joins
```

The lab uses Shamir seal with:

```text
3 key shares
2 key threshold
```

After initialization, the role:

1. stores initialization material locally
2. unseals `vault-1`
3. joins `vault-2` and `vault-3`
4. unseals those nodes
5. creates the platform administration policy
6. creates a scoped Terraform platform token
7. verifies three Raft voters

The result I want to see is boring:

```text
vault-1    voter
vault-2    voter
vault-3    voter
```

Boring infrastructure is usually a compliment.

# Terraform comes back from the other side

This is the architectural decision I like most.

Terraform appears twice.

But they are two completely independent Terraform states.

The first:

```text
terraform/infra/
```

manages things **outside Vault**.

The second:

```text
terraform/platform/
```

manages things **inside Vault**.

That gives me:

```text
Terraform
   |
   +--> Infrastructure state
   |       |
   |       +--> VM substrate
   |
   +--> Platform state
           |
           +--> Vault namespaces
           +--> Vault mounts
           +--> policies
           +--> auth configuration
```

The second layer only runs after the Vault cluster exists and passes validation.

It authenticates using the scoped platform token, not the root token.

The initial configuration creates two Vault Enterprise namespaces:

```text
engineering
operations
```

Inside them:

```text
engineering/
├── kv/
└── transit/

operations/
└── pki/
```

That gives the lab three very different Vault capabilities.

KV v2 demonstrates secrets storage and versioning.

Transit demonstrates cryptography as a service without Vault storing application plaintext.

PKI demonstrates certificate issuance and lifecycle management.

And because the resources are managed by Terraform, manual configuration changes become detectable drift.

The operating workflow is:

```bash

```

The last command should report no changes.

That final clean plan is not cosmetic.

It proves idempotency.

# Idempotency became a feature, not a slogan

This lab is designed around resume points.

If something breaks during TLS creation, fix TLS and rerun the TLS role.

If a Vault binary is missing, rerun installation.

If the platform token expires, rerun bootstrap.

If Vault configuration is changed, rerun configuration.

The implementation deliberately checks existing state before modifying it.

That means failure looks like:

```text
run
 |
 X
 |
fix
 |
rerun same phase
 |
continue
```

rather than:

```text
run
 |
 X
 |
delete everything
 |
pray differently
```

For a learning environment, that distinction is huge.

Failures become observable rather than disposable.

# Validation matters more than deployment

A deployment command returning exit code zero does not mean I have a healthy Vault cluster.

So:

```bash
make validate
```

checks the things that actually matter:

* Vault service active
* RHEL architecture correct
* SELinux enforcing
* swap disabled
* firewall configuration present
* Vault initialized
* nodes unsealed
* one active node
* two standby nodes
* three Raft voters
* Enterprise license loaded and valid

That is much closer to an acceptance test than:

```text
terraform apply completed successfully
```

The project also contains a manual failover test.

First determine the current active node.

Then stop Vault on it.

Today the local Multipass implementation can do that using Multipass.

A more substrate-neutral implementation can perform the same operation through Ansible:

```bash
ansible <active-node> \
  -b \
  -m ansible.builtin.systemd_service \

```

That is another example of removing the hypervisor from the layers above it.

The remaining Vault nodes should elect a new active node.

Restart the original node, unseal it, and validate again.

The expected end state:

```text
1 active
2 standby
3 voters
```

# Terraform versus Ansible was the wrong question

There are endless discussions around:

> Terraform or Ansible?

After building this, I think that question is usually too simplistic.

They solve different problems particularly well.

Terraform is excellent at declaring:

> These infrastructure resources should exist.

Ansible is excellent at declaring:

> These machines should have this configuration.

Vault's Terraform provider is excellent at declaring:

> These Vault resources should exist.

That produced a cleaner model:

```text
Terraform
   Own the VM lifecycle

Ansible
   Own the operating system and Vault installation

Vault
   Own secrets, identity and cryptographic services

Terraform again
   Own Vault's logical platform configuration
```

Nobody has to win.

They just need clearly defined jobs.

# The hypervisor should not win either

The same applies to virtualization platforms.

The question should not be:

> Multipass or VMware?

It should be:

> What contract does the next layer require?

For this architecture, the answer is relatively small:

```text
A supported RHEL machine
A hostname
An address
SSH connectivity
Enough CPU, memory and storage
Connectivity to the other Vault nodes
```

If Multipass provides that, good.

If vSphere provides that, good.

If AWS provides that, good.

If a physical RHEL server provides that, also good.

The substrate changes.

The Vault architecture does not.

That is a much healthier form of portability than pretending every provider has the same resources and syntax.

They do not.

What can remain stable is the **interface between the layers**.

# The ansible/ansible Terraform provider

There is a community Terraform provider that creates `ansible_host`, `ansible_group` and `ansible_playbook` as actual Terraform resources.

That means a Terraform apply can:

1. Create the Multipass VMs
2. Register them as Ansible inventory
3. Run the Ansible playbook
4. Wait for exit zero
5. Continue with downstream Terraform resources

Terraform's dependency graph does the ordering.

The playbook is not a shell command someone fires separately.

It is a node in the graph.

If it fails, the graph stops.

If it succeeds, the graph continues.

That is the explicit baton I was looking for.

# A third Terraform root

The implementation added a third Terraform configuration:

```text
terraform/infra/      # VMs and infrastructure
terraform/ansible/    # Ansible orchestration
terraform/platform/   # Vault logical platform
```

The `infra` root creates the machines and writes:

```hcl
output "ansible_nodes" {
  value = {
    for name, node in multipass_instance.vault : name => {
      ansible_host = node.ipv4[0]
      vault_role   = name == local.node_names[0] ? "leader" : "follower"
    }
  }
}
```

The `ansible` root reads that output:

```hcl
data "terraform_remote_state" "deployment" {
  backend = "local"
  config = {
    path = abspath("${path.module}/../infra/terraform.tfstate")
  }
}
```

And runs the playbook with the topology passed as a JSON extra variable:

```hcl
resource "ansible_playbook" "vault_lab" {
  playbook   = "${local.repository_root}/ansible/terraform.yml"
  name       = "localhost"
  replayable = false

  extra_vars = {
    vault_nodes_json         = jsonencode(data.terraform_remote_state.deployment.outputs.ansible_nodes)
    ansible_private_key_file = "${local.repository_root}/.secrets/ansible/id_ed25519"
    ansible_known_hosts_file = "${local.repository_root}/.secrets/ansible/known_hosts"
    automation_digest        = local.automation_digest
  }
}
```

No inventory file.

No custom Python script.

No `ansible-inventory` plugin with a first-apply timing problem.

The topology arrives as a typed JSON blob, and the playbook builds its own in-memory inventory from it.

# The first-apply problem and how it disappears

The `cloud.terraform` inventory plugin — which would have been the natural alternative — has a documented race condition.

On first apply, the VMs do not yet exist in state.

The inventory plugin reads state.

So on first apply, the inventory is empty.

Workarounds exist, but they are all awkward.

The approach here sidesteps the race entirely.

The `ansible` root is a separate Terraform configuration.

It only runs after `terraform/infra` has completed and written real IP addresses into state.

There is no timing problem because there is no shared apply.

The first root finishes.

The second root reads the finished output.

Clean handoff.

# Terraform can see Ansible's result

After the playbook completes, the provider exposes:

```hcl
ansible_playbook.vault_lab.ansible_playbook_stdout
ansible_playbook.vault_lab.ansible_playbook_stderr
```

I chose not to parse stdout.

That is fragile.

Instead the contract is simple:

> Ansible exits zero, or Terraform stops.

The Ansible `vault_validate` role runs as the final step.

It checks:

```text
Vault service active
Vault initialized
Vault unsealed
three Raft voters
Enterprise license valid
TLS reachable
platform token exists
```

If any assertion fails, the playbook exits non-zero.

Terraform marks `ansible_playbook.vault_lab` as failed.

The `platform` layer never runs.

Exit zero means the cluster is ready.

That is a real acceptance contract, not a cosmetic green banner.

# The provider token problem

There is one complication worth being honest about.

The `platform` Terraform root uses the HashiCorp Vault provider.

That provider needs:

```text
VAULT_ADDR
VAULT_CACERT
VAULT_TOKEN
```

The first two are easy.

Terraform already knows the VM IP and the CA path from `infra` state.

The problem is `VAULT_TOKEN`.

The Ansible bootstrap role creates the scoped platform token.

That token is written to `.secrets/platform-token`.

But Terraform provider configuration is evaluated before the apply graph runs.

It cannot reference a value computed halfway through the same apply.

So the two Terraform configurations must stay separate.

`terraform/platform` reads the token from the file that Ansible wrote.

That is the only seam.

```bash
VAULT_TOKEN="$(<.secrets/platform-token)"
```

It is small.

It is explicit.

And it means the token never appears in Terraform state.

# The automation_digest

One more detail.

`replayable = false` means Terraform will not re-run the playbook on a normal apply once it is recorded in state.

But if I change an Ansible role, a template or a policy, I want re-convergence to be automatic.

The `ansible` root computes:

```hcl
locals {
  automation_files = sort(concat(
    [for f in fileset("${local.repository_root}/ansible", "**/*.yml") : "ansible/${f}"],
    [for f in fileset("${local.repository_root}/ansible", "**/*.j2")  : "ansible/${f}"],
    [for f in fileset("${local.repository_root}/templates", "**/*")   : "templates/${f}"],
    ["policies/platform-admin.hcl"],
  ))
  automation_digest = sha256(join("", [
    for f in local.automation_files : filesha256("${local.repository_root}/${f}")
  ]))
}
```

That digest is passed as an `extra_var`.

If any automation file changes, the digest changes.

Terraform sees a difference in the resource arguments.

The resource is replaced.

The playbook runs again.

I do not have to remember to pass `-replace` manually.

Content-driven re-convergence is built into the graph.

# What actually changed

The layers did not change.

The responsibilities did not change.

What changed is that the **transitions between layers are now structural**, not procedural.

Before:

```text
Human decides to run Ansible after Terraform finishes.
```

After:

```text
Terraform dependency graph ensures Ansible runs after Terraform finishes.
Terraform dependency graph ensures platform runs after Ansible finishes.
```

That difference is small to describe.

It is significant in practice.

In a project that gets picked up after a week away, after a failed run, or by someone else entirely, explicit structure beats documented convention every time.

# The part I would keep, updated

If I rebuilt this tomorrow I would still keep:

> **Automate boundaries, not just commands.**

But I would add one more:

> **Make the transitions between tools as explicit as the tools themselves.**

Calling Ansible from a shell script that runs after Terraform is a convention.

Expressing Ansible as a node in Terraform's dependency graph is a contract.

Contracts survive context switches.

Conventions require people to remember them.

And for a lab that exists to be destroyed, rebuilt and experimented with:

Contracts win.

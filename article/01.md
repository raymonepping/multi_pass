# I Wanted Three Vault VMs on My Mac

## How Terraform, Ansible, RHEL 9 and Vault Enterprise became a portable, one-command deployment pipeline

It started with a fairly innocent requirement.

I wanted three RHEL 9 virtual machines on my Mac, with Vault Enterprise running as a proper three-node Integrated Storage cluster. TLS, Raft, initialization, unseal, namespaces, secret engines, failover testing and drift detection included.

I also wanted to be able to destroy the whole thing and rebuild it.

And I did not want:

```bash
terraform apply
```

to secretly mean:

> Execute a giant pile of shell commands and hope everything eventually looks right.

That distinction turned out to matter much more than I expected.

What started as a small local Vault lab became an exercise in deciding exactly which tool should own which part of the system, how those tools should exchange state, and where automation should deliberately stop.

Eventually the architecture looked like this:

```text
                    macOS / Apple Silicon
                             |
                             v
                    Terraform: infra
                             |
                             v
                        Multipass
                             |
              +--------------+--------------+
              |              |              |
           vault-1         vault-2        vault-3
           RHEL 9          RHEL 9         RHEL 9
           ARM64           ARM64          ARM64
              |              |              |
              +--------------+--------------+
                             |
                             v
                           Ansible
                             |
                  TLS / Vault / systemd
                  license / configuration
                  bootstrap / validation
                             |
                             v
                    Vault Enterprise
                    Integrated Storage
                           Raft
                             |
                             v
                   Terraform: platform
                             |
                +------------+------------+
                |                         |
           engineering                operations
           KV v2                      PKI
           Transit
```

That was already useful.

But it wasn't yet the interesting part.

The interesting part was discovering that none of those tools needed to own the entire workflow.

They only needed to know exactly when to pass the baton.

---

# Why actual RHEL VMs?

I already run plenty of infrastructure locally in containers.

Vault works perfectly well in containers for development and many demo scenarios, and if my goal had simply been to expose port 8200 and show a KV secret, Docker would have been the obvious choice.

That was not what I wanted to test.

I wanted an environment that behaved more like the systems I discuss with customers:

* RHEL
* systemd
* SELinux
* firewalld
* persistent filesystems
* TLS files with real ownership and permissions
* multiple hosts
* Vault running as a system service
* Raft communication between machines
* operating-system state that actually matters

Containers intentionally abstract some of that away.

For this lab, I wanted those details to remain visible.

So the target became three actual RHEL 9 ARM64 virtual machines running locally on an Apple Silicon Mac.

---

# Why Multipass?

My obvious first thought was VMware Fusion.

Fusion is perfectly capable of running ARM64 Linux guests on Apple Silicon.

But the question was not really:

> Can VMware create three VMs?

Of course it can.

The question was:

> What should own their lifecycle?

I wanted the VM layer to be lightweight, scriptable, reproducible, easy to destroy, friendly to cloud-init, and usable from Terraform.

Multipass fitted that local-lab requirement nicely.

It is open source, has a straightforward CLI, runs well on macOS, and a Terraform provider exposes the Multipass lifecycle declaratively.

There is an important nuance here: the Terraform provider I use for Multipass is community maintained. That is a trade-off I was comfortable making for a local lab because the interface is deliberately small.

Terraform needs to create three machines.

That is it.

And keeping that interface small led to the first architectural realization.

---

# Multipass is not the architecture

I did not actually design:

```text
Vault on Multipass
```

I designed:

```text
Vault on three RHEL machines
```

Multipass happens to create those machines in the current implementation.

The layers above it require a relatively small contract:

```text
hostname
IPv4 address
SSH connectivity
RHEL 9
CPU / memory / storage
node-to-node connectivity
```

Once those conditions exist, Ansible can take over.

That means the underlying infrastructure could change without changing the Vault architecture.

Today:

```text
terraform/infra
      |
      v
todoroff/multipass
      |
      v
Multipass
```

Tomorrow:

```text
terraform/infra
      |
      v
vmware/vsphere
      |
      v
vSphere
```

Or another infrastructure implementation entirely.

Conceptually, the substrate could be:

```text
Multipass
VMware vSphere
VMware Cloud Foundation
Parallels
KVM / libvirt
Proxmox
AWS
Azure
Google Cloud
physical RHEL
```

The Terraform resources would obviously differ.

The provider syntax would differ.

Networking would differ.

Image management would differ.

That is fine.

What should remain stable is the contract handed to the next layer.

Something like:

```hcl
nodes = {
  vault-1 = {
    hostname = "vault-1"
    ipv4     = "192.168.1.101"
    ssh_user = "ubuntu"
  }

  vault-2 = {
    hostname = "vault-2"
    ipv4     = "192.168.1.102"
    ssh_user = "ubuntu"
  }

  vault-3 = {
    hostname = "vault-3"
    ipv4     = "192.168.1.103"
    ssh_user = "ubuntu"
  }
}
```

Ansible should care about that object.

It should not care which hypervisor produced it.

That is a much more useful definition of portability than pretending every infrastructure provider behaves the same way.

# Before automating anything, prove the layers

I deliberately started manually.

First with an Ubuntu VM, just to prove the basic Multipass lifecycle:

```bash
multipass launch 24.04 \
  --name mp-test \
  --cpus 2 \
  --memory 2G \
  --disk 10G
```

The guest came up as:

```text
aarch64
```

Networking worked.

Stop and start worked.

Deletion worked.

Then I moved to the real target:

```bash
multipass launch \
  file:///Users/Shared/rhel-9.8-aarch64-kvm.qcow2 \
  --name rhel9-test \
  --cpus 2 \
  --memory 4G \
  --disk 20G
```

And there it was:

```text
Red Hat Enterprise Linux release 9.8 (Plow)
aarch64
```

Native ARM64 RHEL running locally on my Mac.

The VM booted.

SSH worked.

Networking worked.

The filesystem expanded correctly.

And yet:

```bash
cloud-init status
```

reported:

```text
status: error
```

That was the first useful failure.

---

# An Ubuntu assumption hiding inside RHEL

The actual cloud-init failure was:

```text
Command: ['dnf', '-y', 'install', 'pollinate']
```

Multipass had injected vendor data containing:

```yaml
packages:
  - pollinate
```

That makes sense in Ubuntu's ecosystem.

It makes considerably less sense inside a clean RHEL guest with no enabled repositories.

Almost everything had worked, but cloud-init's final stage still failed because the host platform had introduced an assumption about the guest operating system.

My first attempt looked obvious:

```yaml
packages: []
```

It did not work.

Cloud-init's merge behaviour preserved the vendor package list.

The eventual fix was deliberately narrow:

```yaml
#cloud-config

bootcmd:
  - [touch, /var/lib/cloud/instance/sem/config_package_update_upgrade_install]

package_update: false
package_upgrade: false
```

That semaphore tells cloud-init that the package installation module has already completed.

The useful parts remain:

* networking
* users
* SSH keys
* hostname configuration
* growpart
* filesystem resizing

After rebuilding:

```text
status: done
extended_status: done
errors: []
```

and:

```bash
systemctl --failed
```

returned:

```text
0 loaded units listed.
```

`pollinate` is not particularly exciting.

The lesson was.

Had I introduced Terraform, Ansible, Vault, TLS, Raft, cloud-init, Multipass and RHEL simultaneously, that failure could have appeared to originate almost anywhere.

Because I had proved the layers one by one, I knew exactly where to look.

That principle survived the rest of the project:

> Make each layer independently observable before connecting it to the next one.

---

# Terraform owns machines

Once the VM lifecycle was proven, Terraform could take ownership.

The infrastructure root has a simple responsibility:

> Make three healthy RHEL machines exist.

```text
terraform/infra/
```

owns:

```text
vault-1
vault-2
vault-3
```

Each starts with:

```text
2 CPUs
4 GB RAM
20 GB disk
RHEL 9 ARM64
```

Terraform also owns the information discovered while creating those machines, especially their current IP addresses.

That matters because IP addresses are runtime values.

They do not belong in a manually maintained inventory file or a generated `terraform.tfvars`.

Terraform already knows them.

So it exports them.

Conceptually:

```hcl
output "ansible_nodes" {
  value = {
    for name, node in multipass_instance.vault : name => {
      ansible_host = node.ipv4[0]
      vault_role   = name == local.node_names[0] ? "leader" : "follower"
    }
  }
}
```

This output is more important than it first appears.

It is the first baton.

Terraform is not merely saying:

> I finished creating some VMs.

It is saying:

> Here is the topology I created. This is what the next control plane may depend on.

---

# Then Ansible takes over

Once the machines exist, Terraform's job at that layer is done.

Now the question changes from:

> What infrastructure should exist?

to:

> What should these machines look like?

That is where Ansible fits naturally.

The Ansible implementation handles the guest and Vault lifecycle:

```text
RHEL preparation
TLS
Vault installation
Vault Enterprise license
Vault configuration
systemd
bootstrap
unseal
Raft join
validation
```

The roles are deliberately separable so I can work on one phase without rebuilding everything.

If TLS is wrong, I want to debug TLS.

If the Vault binary is wrong, I want to debug installation.

If bootstrap fails, I want to resume at bootstrap.

I do not want every failure to mean:

```text
destroy everything
recreate everything
hope differently
```

The roles are therefore written to converge existing state.

Rerunning the automation should leave correct state alone and repair only what changed.

That makes failures useful rather than disposable.

---

# TLS is real

I also did not want the finished lab to cheat with:

```hcl
tls_disable = true
```

Ansible generates a local CA and individual certificates for the Vault nodes.

Each node certificate contains the appropriate SANs.

The certificates are installed with the correct ownership and permissions on the RHEL guests.

If a VM is rebuilt and receives another address, the automation can detect that the certificate no longer matches and regenerate what is required.

So even on a laptop, the communication path is real:

```text
client
   |
   | TLS
   v
Vault API :8200


vault-1
   |
   | cluster communication
   v
vault-2 / vault-3 :8201
```

It is a lab.

There is no requirement for it to be unnecessarily fake.

---

# A secrets platform should not leak secrets while being built

This sounds obvious.

It still needs to be designed explicitly.

Bootstrap produces highly sensitive material:

```text
.secrets/
├── keys/
│   └── vault.hclic
├── tls/
│   ├── ca.key
│   └── node private keys
├── vault-init.json
└── platform-token
```

The initialization material contains the initial root token and Shamir unseal keys.

Those do not belong in Git.

They do not belong in Terraform variables.

They do not belong in Terraform outputs.

And they certainly do not belong in Terraform state just because Terraform happens to be orchestrating part of the deployment.

Sensitive Ansible tasks use:

```yaml
no_log: true
```

Local files receive restrictive permissions.

The initial root token remains break-glass material.

The later Terraform platform layer receives a deliberately scoped Vault token instead.

That creates an important boundary:

> Terraform may manage Vault without owning Vault's bootstrap secrets.

The platform Terraform configuration should manage secret infrastructure such as namespaces, mounts, policies and authentication configuration.

It does not need to become another place where application secrets are stored.

# Bootstrapping Raft

The bootstrap phase turns three independent Vault processes into one Vault cluster.

The lab uses Shamir seal with:

```text
3 key shares
2 key threshold
```

The sequence is roughly:

```text
vault-1
   |
   +--> initialize
   |
   +--> unseal
   |
   +--> first Raft member
              |
              +--> vault-2 joins
              |
              +--> vault-3 joins
```

The automation then:

1. stores initialization material locally
2. unseals `vault-1`
3. joins `vault-2`
4. joins `vault-3`
5. unseals the followers
6. creates the platform administration policy
7. creates a scoped platform token
8. verifies the resulting cluster

The end state should be boring:

```text
vault-1    voter
vault-2    voter
vault-3    voter
```

Boring infrastructure is usually a compliment.

# Terraform comes back

This was already one of the decisions I liked most about the architecture.

Terraform appears twice, but for two different reasons.

The first root:

```text
terraform/infra/
```

owns things outside Vault.

The final root:

```text
terraform/platform/
```

owns things inside Vault.

Those states remain deliberately separate.

```text
Terraform: infra
      |
      +--> VM lifecycle
      +--> addresses
      +--> topology


Terraform: platform
      |
      +--> namespaces
      +--> mounts
      +--> policies
      +--> auth configuration
```

The platform root authenticates using the scoped platform token, not the initial root token.

Its initial desired state includes:

```text
engineering/
├── kv/
└── transit/

operations/
└── pki/
```

That gives the lab several different Vault capabilities.

KV v2 demonstrates versioned secret storage.

Transit demonstrates cryptography as a service.

PKI demonstrates certificate issuance and lifecycle.

Namespaces demonstrate administrative isolation inside Vault Enterprise.

And because those resources are expressed in Terraform, manual changes become visible as drift.

A successful deployment is not complete until the platform plan is clean.

# The first realization

At that point I thought the architecture was essentially finished.

Then I looked at it again.

Multipass was not really part of the Vault architecture.

It was just the current implementation of the lowest layer.

Replace that Terraform provider and the same topology contract can describe VMs somewhere else.

The same Ansible roles can configure RHEL.

The same Vault bootstrap logic can form the cluster.

The same final Terraform layer can configure Vault.

The stable interface is:

```text
Infrastructure provider
         |
         v
reachable RHEL machines
         |
         v
      Ansible
         |
         v
Vault Enterprise / Raft
         |
         v
Terraform platform
```

I stared at that for a second.

**Fuck.**

I hadn't really built a Multipass Vault lab.

I had built the beginnings of a portable Vault deployment architecture.

Multipass was just provider number one.

# But there was still a problem

The layers were clean.

The responsibilities were clean.

The interfaces were becoming clear.

But the transitions were still human.

A deployment still looked something like:

```bash
make infra

make ansible-deps
make ansible-ssh
ansible-playbook ansible/site.yml

make validate

make platform
make platform-validate
```

That is automated work, but the workflow itself is still a checklist.

Terraform does something.

I decide that it finished correctly.

Then I launch Ansible.

I decide that Ansible finished correctly.

Then I launch Terraform again.

Every gap is a place where I can forget a step, run something out of order, or come back later and wonder exactly where I stopped.

The layers were automated.

The **handoffs were not**.

That became the next problem.

# The missing piece was the baton

The workflow I wanted was simple to describe:

```text
Terraform creates the machines
        |
        v
Terraform hands the topology to Ansible
        |
        v
Ansible converges RHEL and Vault
        |
        v
Ansible proves the cluster is healthy
        |
        v
Terraform continues and configures Vault
```

I wanted that to be literal.

Not:

```text
Human remembers what comes next
```

but:

```bash
make lab
```

One human action.

Multiple deliberately separated control planes.

That distinction matters.

"One command" does not mean "one enormous Terraform state."

In fact, I specifically did **not** want that.

# The Ansible Terraform provider

The `ansible/ansible` Terraform provider provided the missing integration.

It exposes Ansible execution as Terraform resources, including `ansible_playbook`.

That means Ansible no longer has to be an unrelated command somebody happens to run after Terraform.

Terraform can own the Ansible execution itself.

The final implementation introduced a third Terraform root:

```text
terraform/
├── infra/
├── ansible/
└── platform/
```

Their responsibilities are now extremely explicit.

```text
terraform/infra
    |
    | creates VMs
    | exports topology
    v

terraform/ansible
    |
    | consumes topology
    | executes Ansible
    | waits for success
    v

terraform/platform
    |
    | authenticates to healthy Vault
    | applies logical Vault state
    v
```

That is the baton.

---

# Passing topology instead of rediscovering it

The infrastructure root already knows the nodes.

So the Ansible root reads the completed infrastructure outputs:

```hcl
data "terraform_remote_state" "deployment" {
  backend = "local"

  config = {
    path = abspath("${path.module}/../infra/terraform.tfstate")
  }
}
```

Then it passes that topology into the playbook:

```hcl
resource "ansible_playbook" "vault_lab" {
  playbook   = "${local.repository_root}/ansible/terraform.yml"
  name       = "localhost"
  replayable = false

  extra_vars = {
    vault_nodes_json         = jsonencode(
      data.terraform_remote_state.deployment.outputs.ansible_nodes
    )

    ansible_private_key_file = "${local.repository_root}/.secrets/ansible/id_ed25519"
    ansible_known_hosts_file = "${local.repository_root}/.secrets/ansible/known_hosts"
    automation_digest        = local.automation_digest
  }
}
```

Ansible receives the complete topology as structured JSON and creates its in-memory inventory from that data.

No manually maintained inventory.

No duplicate IP addresses in configuration files.

No custom Python inventory script.

No need for Ansible to rediscover information Terraform already owns.

That is the contract:

```text
Terraform knows what it created.

Ansible consumes exactly that.
```

# Why separate Terraform roots help

At first it might seem cleaner to put everything into one giant Terraform configuration.

Create VMs.

Run Ansible.

Configure Vault.

Done.

But the boundaries become valuable here.

The infrastructure root must finish before the Ansible root consumes its outputs.

That removes first-run ambiguity.

The second root reads a completed state snapshot containing real VM addresses.

Conceptually:

```text
terraform/infra apply
        |
        | writes completed outputs
        v
terraform/ansible apply
        |
        | reads completed outputs
        v
ansible_playbook
```

There is no need for an inventory mechanism to look at infrastructure state before that state actually contains the machines.

The first control plane finishes.

The next one receives its return values.

Simple.

---

# Terraform can react to Ansible

This is where the integration becomes much more than a prettier shell wrapper.

Inside the Ansible Terraform root, the playbook is a real resource:

```text
data.terraform_remote_state.deployment
                  |
                  v
      ansible_playbook.vault_lab
```

Terraform waits for that resource.

Ansible runs.

If the playbook fails, the Terraform apply fails.

If the playbook succeeds, Terraform marks the resource successful.

I deliberately do not parse human-readable Ansible stdout to determine whether Vault is healthy.

The contract is stronger than that.

The final Ansible validation phase asserts the actual conditions I care about:

```text
Vault service active
Vault initialized
Vault unsealed
TLS reachable
Enterprise license valid
three Raft voters
platform token exists
```

If one of those conditions is false, Ansible exits non-zero.

Terraform sees a failed resource.

The `terraform/ansible` apply fails.

The top-level orchestration stops.

The platform root is never invoked.

That is an actual acceptance gate.

Not a green banner printed by a script.

# The one seam that should remain

There is still one interesting boundary.

The final Terraform root uses the Vault provider.

That provider needs:

```text
VAULT_ADDR
VAULT_CACERT
VAULT_TOKEN
```

The Vault API addresses are already known from the infrastructure outputs.

The CA certificate lives at a deterministic local path after the TLS phase.

But `VAULT_TOKEN` does not exist until Ansible bootstraps Vault and creates the scoped platform credential.

Terraform provider configuration is evaluated before the resources in that Terraform operation are applied.

So a Vault provider cannot cleanly depend on a token that another resource will only create halfway through the same apply.

Trying to force that into one Terraform graph would make the design worse.

The correct answer is to preserve the seam.

Ansible writes:

```text
.secrets/platform-token
```

Then, and only then, a new Terraform process starts for the platform root.

Conceptually:

```text
Terraform: infra
      |
      v
Terraform: ansible
      |
      v
Ansible bootstrap
      |
      +--> .secrets/platform-token
      |
      v
Terraform: platform
```

The token never has to become a Terraform output.

It never needs to enter infrastructure state.

It exists only long enough, and in the correct place, for the next control plane to authenticate.

That is not an unfortunate workaround.

It is a useful security boundary.

# Why `make lab` still matters

There is an important distinction here.

Terraform's dependency graph does not magically span three independent Terraform roots.

Inside `terraform/ansible`, Terraform owns the dependency between completed infrastructure outputs and the `ansible_playbook` resource.

But the top-level sequence:

```text
infra
  -> ansible
     -> platform
```

is orchestrated by `make lab`.

That is a feature, not something to hide.

Each Terraform root owns its own declarative state.

The orchestration layer owns when one control plane may hand responsibility to the next.

So the final architecture is not:

> Terraform owns absolutely everything.

It is:

> Each tool owns the state it understands best, and the orchestration layer makes the transitions deterministic.

That is a much cleaner claim.

# Re-convergence should react to code changes too

There was one more problem to solve.

The Ansible playbook resource uses:

```hcl
replayable = false
```

because I do not want Terraform to run the complete convergence path on every ordinary apply when nothing changed.

But what happens if I change an Ansible role?

Or a Jinja template?

Or the Vault platform administration policy?

Terraform needs some way to know that the automation itself changed.

The solution is an automation digest.

The Ansible Terraform root calculates a hash across the files that define convergence:

```hcl
locals {
  automation_files = sort(concat(
    [for f in fileset("${local.repository_root}/ansible", "**/*.yml") :
      "ansible/${f}"
    ],
    [for f in fileset("${local.repository_root}/ansible", "**/*.j2") :
      "ansible/${f}"
    ],
    [for f in fileset("${local.repository_root}/templates", "**/*") :
      "templates/${f}"
    ],
    ["policies/platform-admin.hcl"],
  ))

  automation_digest = sha256(join("", [
    for f in local.automation_files :
      filesha256("${local.repository_root}/${f}")
  ]))
}
```

That digest is passed to the `ansible_playbook` resource as an extra variable.

If the automation content changes, the resource configuration changes.

Terraform detects the update and the provider executes the playbook again.

So re-convergence becomes content driven.

I do not have to remember:

> I changed a role, therefore I should probably run Ansible manually.

The graph knows the automation definition changed.

That is another small handoff converted from convention into structure.

# Validation matters more than deployment

A deployment command returning exit code zero does not prove that I have a healthy Vault cluster.

So the project validates the state independently.

The checks include:

* Vault service active
* RHEL architecture correct
* SELinux enforcing
* swap disabled
* firewall configuration present
* Vault initialized
* nodes unsealed
* exactly one active node
* remaining nodes standby
* three Raft voters
* Enterprise license loaded and valid
* TLS connectivity
* clean Vault platform Terraform plan

There is also a failover test.

Stop Vault on the active node.

Wait for another voter to become active.

Restart the original node.

Unseal it.

Validate again.

The target state remains:

```text
1 active
2 standby
3 voters
```

The interesting metric is not:

```text
terraform apply succeeded
```

It is:

```text
the desired system exists,
behaves correctly,
survives failure,
and produces no drift
```

---

# And then check the state itself

The last acceptance check is one of my favourites:

```text
check-state-secrets.sh
```

Because a Vault lab is not successful if the automation leaked the things Vault is supposed to protect into Terraform state.

So after all three control planes have converged, the project checks that credentials did not accidentally end up there.

That includes the material I explicitly wanted to keep outside Terraform:

```text
initial root token
Shamir unseal keys
Vault Enterprise license contents
TLS private keys
platform authentication material
```

The final criterion is therefore not simply:

> Vault works.

It is:

> Vault works, the environment is reproducible, the platform is drift-clean, and the automation did not violate the security boundaries it was supposed to demonstrate.

That feels like a much more appropriate definition of done.

# I kept the shell path too

There is still a shell-driven implementation beside the Ansible path.

I like having it.

The shell path exposes the individual transitions clearly, which makes it useful while learning or investigating a particular phase.

Ansible is better for repeated convergence and portability.

The one-command path is better when I want the entire environment.

They are different interfaces onto the same architecture.

That means I can choose whether I want to study the machinery or simply use it.

# Terraform versus Ansible was the wrong question

There are endless discussions framed as:

> Terraform or Ansible?

After building this, I think that framing misses the interesting part.

Terraform is very good at declaring:

> These infrastructure resources should exist.

Ansible is very good at declaring:

> These machines should have this configuration.

Vault is responsible for:

> This is the security and trust state of the platform.

And Terraform's Vault provider is very good at declaring:

> These logical Vault resources should exist.

So the final ownership model is:

```text
Terraform: infra
    Own VM lifecycle and topology

Ansible
    Own RHEL and Vault convergence

Vault
    Own secrets, identity and cryptographic services

Terraform: platform
    Own logical Vault configuration

make lab
    Own the transitions between those control planes
```

Nobody has to win.

They just need clearly defined jobs.

# What I actually built

What started as:

> Deploy three VMs and install Vault.

ended up as:

```text
                         make lab
                            |
                            v
                    Terraform: infra
                            |
                    VM provider contract
                            |
                            v
                    Three RHEL nodes
                            |
                            v
                   Terraform: ansible
                            |
                    ansible_playbook
                            |
                            v
                         Ansible
                            |
             +--------------+--------------+
             |              |              |
            TLS          Vault/Raft     Validation
             |              |              |
             +--------------+--------------+
                            |
                      platform token
                            |
                            v
                   Terraform: platform
                            |
                 +----------+----------+
                 |                     |
            engineering            operations
            KV / Transit              PKI
```

The current infrastructure substrate happens to be Multipass on Apple Silicon.

That is deliberately not the architectural ceiling.

The system now gives me:

* reproducible infrastructure
* replaceable VM provisioning
* real RHEL guests
* native ARM64
* TLS
* Vault Enterprise
* Integrated Storage
* three-node Raft
* Shamir initialization and unseal
* scoped automation credentials
* namespaces
* KV v2
* Transit
* PKI
* Terraform-to-Ansible topology handoff
* idempotent convergence
* independent health validation
* failover testing
* Terraform drift detection
* state-secret validation
* complete teardown and rebuild
* one-command deployment

All locally on my Mac.

But the more important part is what is **not** tied to my Mac.

Replace the infrastructure adapter and the same higher-level contracts can survive.

# The part I would keep

If I rebuilt this project tomorrow, I would keep one principle above everything else:

> **Automate boundaries, not just commands.**

A command tells a tool to do something.

A boundary tells the next tool what it may safely assume.

Terraform should not merely finish creating VMs.

It should return a topology.

Ansible should not merely finish running tasks.

It should prove that Vault is healthy enough for the next control plane.

Terraform's Vault provider should not bootstrap the cluster just because Terraform technically happens to be present.

It should begin only after a valid Vault platform exists.

And bootstrap credentials should not enter Terraform state simply because that would make the wiring easier.

The second principle is the one I learned later:

> **Make the transitions between tools as explicit as the tools themselves.**

Calling Ansible manually after Terraform is a convention.

Making Ansible an explicit Terraform-managed stage, and refusing to advance to the next control plane until it succeeds, is a contract.

Contracts survive context switches.

Conventions require people to remember them.

For a lab specifically designed to be destroyed, rebuilt, modified and broken on purpose, that distinction matters.

I started by wanting three Vault VMs on my Mac.

What I ended up with was much more useful:

```bash
make lab
```

One human action.

Several independent control planes.

Clear ownership.

Explicit handoffs.

No bootstrap secrets in Terraform state.

And a fully converged Vault Enterprise platform at the other end.

**Contracts win.**
